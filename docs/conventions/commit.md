# 커밋·브랜치·PR

## 커밋 메시지

```text
type(scope): 한국어 요약

본문(선택) — 왜 바꿨는지. 무엇을 바꿨는지는 diff가 말해 준다.
```

- **type**: `feat` / `fix` / `docs` / `refactor` / `test` / `chore`
- **scope**: 모듈 디렉터리명 (`api`, `ui`, `worker`) 또는 그룹명 (`edge`, `central`).
  여러 모듈에 걸치거나 대상이 분명하지 않으면 **생략한다** — `docs: 커밋 컨벤션 정리`
- 콜론 앞에 공백을 넣지 않는다. 요약은 마침표 없이 끝낸다. 50자 안팎.
- **`Co-Authored-By` 등 트레일러를 넣지 않는다.** AI 도구가 자동으로 붙이는 줄도 지운다.

예:

```text
feat(api): 장비 상태 조회 API 추가
fix(worker): 전송 실패 시 재시도 간격이 0이 되는 문제 수정
docs: Claude Code 적용 가이드 추가
```

## 커밋 단위

- 한 커밋은 한 가지 이유로 바뀐 파일만 담는다. 리팩토링과 기능 추가를 섞지 않는다.
- 규칙·도구 도입은 그 규칙을 적용한 코드 변경과 같은 커밋에 넣는다.
- `git add .`를 쓰지 않고 파일을 명시한다.

## 브랜치

`<type>/<짧은-설명>` — 예: `feat/device-status-api`, `fix/worker-retry`

## PR 본문

```markdown
## 변경 내용
- <무엇을, 왜>

## 확인 방법
- <실행한 명령과 결과 (테스트 건수)>

## 영향 범위
- <다른 모듈·계약·DB 변경 여부>
```
