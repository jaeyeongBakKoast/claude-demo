# 요구사항 정의서 (제품 백로그)

우선순위가 높은 `accepted` 항목부터 스토리로 가져간다. 한 요구사항이 여러 스토리로 나뉠 수 있다.

- **우선순위**: `M`(Must) · `S`(Should) · `C`(Could) · `W`(Won't, 이번 범위 아님)
- **상태**: `proposed`(제안) → `accepted`(합의) → `in-progress` → `done` / `dropped`
- **출처**: RFP 항목 번호, 회의록, 이해관계자 등. 감리에서 "이 요구사항은 어디서 왔나"에 답하는 칸이다

## 기능 요구사항

| ID | 요구사항 | 우선순위 | 상태 | 출처 | 관련 UC | 스토리 |
|---|---|---|---|---|---|---|
| REQ-F-001 | <예: 운영자는 장비별 최신 상태를 목록으로 조회할 수 있어야 한다> | M | proposed | <RFP 3.2.1> | UC-001 | |

## 비기능 요구사항

| ID | 분류 | 요구사항 | 측정 기준 | 우선순위 | 상태 | 출처 | 검증 |
|---|---|---|---|---|---|---|---|

## 작성 규칙

- 한 행에 하나의 검증 가능한 요구. "편리해야 한다"처럼 확인할 수 없는 문장은 측정 기준을 붙이거나 쪼갠다.
- 비기능 요구사항은 **측정 기준**과 **검증 위치**를 반드시 채운다. R&D 과제의 정량 성능지표는 여기에 `REQ-N`으로 둔다.
